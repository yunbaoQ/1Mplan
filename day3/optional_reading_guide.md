## 第二步：两种方式各写一个函数（15分钟）

建议函数接口（返回字典，不在函数里写JSON）：

```python
count_whole_file(path)
count_line_by_line(path)
```

整文件方式：open UTF-8文件 → f.read()得到完整字符串 → 调用已有word_count → 返回结果。

逐行方式：open UTF-8文件 → 建立总计数字典 → `for line in f` → 调用word_count(line) → 把本行字典累计到总字典 → 返回总字典。

合并提示：遍历本行字典的 `.items()`，某个词的总次数是“此前总次数 + 本行次数”。可用 `.get(word, 0)` 取得不存在时的零，不提供完整循环答案。

直接复用你写好的 word_count 函数定义即可。当前 word_count.py 顶层有打开文件和写JSON动作，直接import它会执行这些动作；这次可只把自己的函数定义复制进选做脚本。主入口组织留到后续学习，不必为选做先重构整个脚本。

逐行方式不要用 `f.readlines()`，它会先把全部行读到列表；也不要把每行拼回一个大字符串。遍历 `for line in f` 才符合这次比较的目标。

可用分析框架：文本长度N、最长行长度L、不同词数量V。整文件计数的额外内存通常随N与V增长；逐行计数主要随L与V增长（还存在IO缓冲、分词与字典开销），并非固定常量。独特词很多时，总字典仍可能很大。文件长度和字典容量是不同的限制。

两者都要读取文件全部内容。逐行有循环及多次函数调用开销；当前清洗函数还有反复replace的成本，所以不能单凭读取方式宣布谁更快。特别注意：你当前函数的最坏清洗时间可能是O(N²)，不要套用“整段算法一定O(N)”的结论。
